# 에이릿 뉴스레터 구독·발송 서비스 설계

## 1. 목적

에이릿 웹사이트에 이메일 뉴스레터 구독 서비스를 추가한다. 방문자는 이메일 주소만 입력해 구독을 신청하고, 확인 메일의 링크를 눌러 구독을 확정한다. 관리자는 기존 에이릿 관리자 화면을 확장한 `에이릿 편집실`에서 뉴스레터를 작성하고 테스트한 뒤 활성 구독자 전체에게 발송한다.

첫 버전은 개인정보와 운영 복잡도를 최소화한다. 관심 분야나 사용자 유형에 따른 구독자 분류, 열람 추적, 클릭 추적은 포함하지 않는다.

## 2. 확정된 원칙

- 기존 Cloudflare Pages, Pages Functions, D1 구조를 유지한다.
- 대량 발송은 요청 한 번에 처리하지 않고 Cloudflare Queue와 전용 소비 Worker로 분리한다.
- 이메일 전달은 Resend를 사용한다.
- 구독은 이메일 확인 링크를 거치는 이중 확인 방식으로 처리한다.
- 구독 시 수집하는 개인정보는 이메일 주소 한 가지다.
- 발송 대상은 관심 분야 구분 없이 모든 활성 구독자다.
- 뉴스레터 본문은 블록형 에디터로 작성한다.
- CMS는 별도 서비스가 아니라 기존 관리자 화면에 통합한다.
- 발송한 뉴스레터의 본문과 대상은 변경되지 않도록 보존한다.
- 열람 및 클릭 추적은 사용하지 않는다.

## 3. 사용자 화면

### 3.1 구독 신청

홈페이지의 뉴스레터 진입 링크와 별도 뉴스레터 구독 페이지를 제공한다. 화면에는 다음 정보만 표시한다.

- `에이릿 뉴스레터` 제목
- `AI 리터러시와 교육에 관한 새 글을 이메일로 보내드립니다.`라는 짧은 설명
- 이메일 주소 입력란
- 구독 신청 버튼
- 뉴스레터 발송용 개인정보 수집·이용 동의 체크박스
- 뉴스레터 개인정보 수집·이용 안내 링크
- 확인 메일의 링크를 눌러야 구독이 완료된다는 설명

‘한 가지 쟁점’, ‘한 가지 판단’, ‘한 가지 도구’와 같은 부가 소개는 넣지 않는다.

### 3.2 뉴스레터 개인정보 수집·이용 안내

기존 회원 개인정보 처리방침과 구분된 뉴스레터 전용 안내 페이지를 만든다. 구독 신청 화면의 `안내 보기` 링크에서 접근할 수 있어야 한다.

안내 페이지에는 다음 내용을 명시한다.

| 항목 | 내용 |
| --- | --- |
| 수집 항목 | 이메일 주소 |
| 이용 목적 | 에이릿 뉴스레터 발송과 구독 상태 관리 |
| 보유 기간 | 구독 취소 시까지. 취소 후 재발송 방지에 필요한 최소 기록은 관계 법령과 운영정책에 따라 보관 |
| 동의 거부 | 동의를 거부할 수 있으나 뉴스레터 구독은 할 수 없음 |
| 처리 위탁 | Resend를 통한 이메일 발송 |

### 3.3 이메일 확인

1. 방문자가 이메일 주소를 입력하고 개인정보 수집·이용에 동의한다.
2. 서버는 신청을 `pending` 상태로 저장하고 24시간 동안 유효한 확인 링크를 Resend로 발송한다.
3. 방문자가 링크를 누르면 구독 상태를 `active`로 변경한다.
4. 만료된 링크에는 새 확인 메일을 요청할 수 있는 경로를 제공한다.
5. 이미 활성 구독 중인 주소에는 중복 신청이 아니라 현재 상태를 안내한다.

### 3.4 구독 취소와 재구독

모든 뉴스레터 하단에 개인별 구독 취소 링크를 넣는다. 링크에는 이메일 주소 원문을 넣지 않고 서버가 검증할 수 있는 서명 토큰을 사용한다. 취소 요청이 여러 번 들어와도 같은 결과를 반환한다.

구독 취소 시 주소를 즉시 물리 삭제하지 않고 상태를 `unsubscribed`로 바꾸고 취소 시각을 기록한다. 이는 실수로 다시 발송하는 일을 방지하기 위한 최소 기록이다. 같은 주소로 재구독을 신청하면 새로운 이메일 확인 절차를 거친다.

## 4. 에이릿 편집실

기존 `admin.html`의 관리자 인증과 `is_admin` 권한을 유지하면서 화면을 `에이릿 편집실`로 확장한다. 주요 메뉴는 다음과 같다.

- 회원
- 답변
- 뉴스레터
- 구독자
- 발송 기록

### 4.1 뉴스레터 목록

제목, 상태, 최종 수정 시각, 작성자, 발송 시각, 발송 대상 수를 표시한다. 상태는 `draft`, `sending`, `sent`, `failed`를 사용한다. 새 뉴스레터 작성과 기존 초안 편집으로 이동할 수 있다.

### 4.2 블록형 편집기

첫 버전이 지원하는 블록은 다음과 같다.

- 제목
- 본문
- 이미지
- 버튼
- 구분선

관리자는 블록을 추가하고, 순서를 바꾸고, 내용을 수정하고, 삭제할 수 있다. 뉴스레터 제목과 받은편지함 미리보기 문구는 본문 블록과 별도로 입력한다. 초안은 자동 저장한다.

이미지는 첫 버전에서 외부 공개 URL을 입력하는 방식으로 제한한다. 별도 이미지 업로드 저장소는 이번 범위에 포함하지 않는다.

### 4.3 검토와 테스트 발송

- 데스크톱과 모바일 너비로 이메일을 미리 볼 수 있다.
- 관리자 본인 또는 관리자가 입력한 한 개의 이메일 주소로 테스트 발송할 수 있다.
- 발송 전 제목, 빈 본문, 잘못된 링크를 검사한다.
- 테스트 메일에는 실제 뉴스레터와 구분되는 표시를 넣는다.

### 4.4 전체 발송

전체 발송 버튼을 누르면 현재 활성 구독자 수와 뉴스레터 제목을 보여주고 최종 확인을 받는다. 같은 뉴스레터에 대한 중복 발송을 막기 위해 발송 시작 시 상태를 원자적으로 `sending`으로 변경하고 발송 키를 기록한다.

발송 대상은 시작 시점에 `active`인 구독자로 고정하고 수신자별 발송 레코드를 먼저 만든다. Pages Function은 최대 100명 단위의 작업을 Cloudflare Queue에 넣고 즉시 관리자 화면에 응답한다. 별도 소비 Worker가 각 작업을 받아 Resend Batch API로 발송하며, 수신자마다 성공 여부와 Resend 메시지 ID를 기록한다. 일부 실패가 발생해도 전체 작업을 중단하지 않고 남은 대상을 계속 처리한다.

실패한 주소만 선택적으로 다시 발송할 수 있다. 재발송 시 이미 성공한 수신자에게는 보내지 않는다. 발송이 시작된 뉴스레터의 제목, 미리보기 문구, 본문 블록은 수정할 수 없다.

### 4.5 발송 결과

발송 기록에서 다음 수치를 확인할 수 있다.

- 전체 대상 수
- 처리 중 수
- 성공 수
- 실패 수
- 발송 시작 및 완료 시각

첫 버전은 열람률과 클릭률을 수집하거나 표시하지 않는다.

## 5. 데이터 모델

### 5.1 `newsletter_subscribers`

| 필드 | 용도 |
| --- | --- |
| `id` | 내부 식별자 |
| `email` | 정규화한 이메일 주소, 유일값 |
| `status` | `pending`, `active`, `unsubscribed`, `bounced`, `complained` |
| `consent_at` | 개인정보 수집·뉴스레터 수신 동의 시각 |
| `confirmed_at` | 이메일 확인 시각 |
| `unsubscribed_at` | 구독 취소 시각 |
| `confirmation_token_hash` | 일회용 확인 토큰의 해시 |
| `confirmation_expires_at` | 확인 링크 만료 시각 |
| `created_at`, `updated_at` | 생성·변경 시각 |

원본 확인 토큰은 데이터베이스에 저장하지 않는다. 이메일은 소문자로 정규화하고 앞뒤 공백을 제거한다.

| `created_by` | 기존 관리자 사용자 ID |

### 5.3 `newsletter_sends`

| 필드 | 용도 |

`send_id`와 `subscriber_id` 조합에는 유일 제약을 둬 같은 작업에서 중복 발송되지 않게 한다.

## 6. 서버 기능

### 6.1 실행 구조

Pages Functions는 공개 구독 API와 관리자 API를 담당한다. 전체 발송 API는 D1에 발송 대상과 중복 방지 상태를 기록한 뒤 Queue 생산자 바인딩으로 묶음 작업을 등록한다. Queue 소비는 Pages Functions가 지원하지 않으므로 별도 Cloudflare Worker가 담당한다. 소비 Worker는 같은 D1 데이터베이스와 Resend 비밀값을 바인딩해 발송 결과를 갱신한다.

이 구조는 브라우저 요청이 끝난 뒤에도 발송이 계속되게 하고, 일시 오류가 발생한 묶음을 안전하게 재시도할 수 있게 한다.

### 6.2 공개 API

- 구독 신청
- 이메일 확인
- 확인 메일 재요청
- 구독 취소

공개 API는 이메일 형식을 검증하고, 봇이 채우는 숨은 입력값을 확인하며, 같은 IP와 이메일의 반복 요청을 제한한다. 응답은 특정 이메일의 등록 여부를 공격자가 쉽게 알아낼 수 없도록 과도한 계정 정보를 노출하지 않는다.

### 6.3 관리자 API

- 뉴스레터 목록·조회·생성·수정
- 테스트 발송
- 전체 발송 시작
- 발송 상태·내역 조회
- 구독자 목록과 상태 조회
- 실패 대상 재발송

모든 관리자 요청은 기존 세션을 검증한 뒤 DB에서 현재 사용자의 `is_admin` 값을 다시 확인한다.

### 6.4 Resend 연동

`RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, 검증된 발신 주소, 공개 사이트 주소는 Cloudflare 비밀값 또는 환경 변수로 관리한다. 브라우저 코드에는 Resend API 키나 내부 발송 자격 증명을 넣지 않는다. 발송 도메인은 평판 분리를 위해 뉴스레터 전용 하위 도메인을 사용한다.

Resend 웹훅은 서명을 검증한 후 처리한다. 영구 반송은 구독자를 `bounced`, 스팸 신고는 `complained` 상태로 바꾸고 이후 발송 대상에서 제외한다.

## 7. 이메일 형식

블록 JSON은 서버에서 제한된 이메일 HTML로 변환한다. 사용자 입력 HTML을 그대로 저장하거나 전송하지 않는다. 제목, 본문, 버튼 문구는 이스케이프하고 링크는 허용된 `https` 및 `http` 주소만 사용한다.

모든 운영 뉴스레터에는 다음을 자동으로 붙인다.

- 에이릿 발신자 표시
- 웹사이트 주소
- 이 메일을 받는 이유
- 개인별 구독 취소 링크
- 표준 `List-Unsubscribe` 및 원클릭 구독 취소 헤더

이메일은 HTML과 일반 텍스트 버전을 함께 발송한다.

## 8. 오류 처리

- 기술 오류 대신 사용자가 다음 행동을 알 수 있는 한국어 문구를 제공한다.
- 확인 링크가 잘못되었거나 만료되면 새 링크 요청 경로를 보여준다.
- 이미 확인되거나 취소된 링크는 안전하게 현재 상태를 안내한다.
- Resend 장애나 일시 오류는 발송 기록에 남기고 실패 대상으로 재시도할 수 있게 한다.
- 발송이 일부만 성공하면 `partial`로 기록하고 성공한 수신자는 재발송 대상에서 제외한다.
- 관리자에게 원본 API 키나 민감한 서버 오류 내용을 노출하지 않는다.

## 9. 보안과 개인정보

- 공개 링크에는 이메일 원문 대신 만료 가능한 서명 토큰을 사용한다.
- 확인 토큰 원문은 저장하지 않고 해시만 저장한다.
- 관리자 API는 로그인과 관리자 권한을 모두 확인한다.
- 발송 시작은 원자적 상태 변경과 중복 방지 키로 보호한다.
- 개인정보 수집 동의 시각을 기록한다.
- 열람 픽셀과 클릭 추적 링크를 사용하지 않는다.
- 개인정보 및 발송 데이터는 필요한 관리자만 볼 수 있게 한다.

## 10. 검증 기준

### 구독

- 신규 신청에서 확인 메일 발송, 링크 확인, 활성화까지 동작한다.
- 중복 신청, 이미 활성화된 주소, 잘못된 주소를 안전하게 처리한다.
- 24시간이 지난 확인 링크는 거부하고 재요청을 제공한다.
- 취소한 주소는 이후 전체 발송 대상에 포함되지 않는다.
- 취소한 주소의 재구독은 새 확인 절차를 요구한다.

### 관리자

- 비로그인 사용자와 일반 회원은 편집실 뉴스레터 기능 및 API에 접근할 수 없다.
- 초안의 블록 추가·수정·정렬·삭제와 자동 저장이 동작한다.
- 미리보기와 테스트 발송 결과가 실제 이메일 내용과 일치한다.
- 빈 제목, 빈 본문, 잘못된 링크가 전체 발송 전에 차단된다.

### 발송

- 활성 구독자에게만 한 번씩 발송된다.
- 중복 클릭이나 요청 재전송으로 중복 발송되지 않는다.
- 부분 실패 시 성공·실패 수치와 수신자 상태가 일치한다.
- 실패 대상 재발송에서 이미 성공한 주소는 제외된다.
- 반송과 스팸 신고 웹훅이 이후 발송을 차단한다.

### 화면과 배포

- 구독 신청과 상태 안내가 모바일과 데스크톱에서 읽기 쉽다.
- 뉴스레터 HTML과 일반 텍스트 버전을 주요 이메일 환경에서 확인한다.
- 로컬 D1에서 기능을 검증한 뒤 Cloudflare Pages 배포 환경에서 공개 URL, 비밀값, Resend 웹훅을 확인한다.
- Queue 생산자와 소비 Worker는 각각 검증하고, 통합 발송은 Cloudflare 미리보기 또는 별도 테스트 환경에서 확인한다.

## 11. 범위에서 제외하는 항목

- 관심 분야 또는 사용자 유형별 구독자 분류
- 예약 발송과 반복 발송
- 열람률 및 클릭률 추적
- A/B 테스트
- 외부 이미지 업로드 저장소
- 여러 관리자 역할과 승인 워크플로
- 기존 회원 이메일의 자동 뉴스레터 구독 전환

기존 회원은 별도의 뉴스레터 수신 동의를 하지 않았으므로 자동으로 구독자에 포함하지 않는다.
